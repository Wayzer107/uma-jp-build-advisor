# ChatGPT web and mobile access

The web experience is the remote MCP App: the advisor returns an interactive view with the trainee, six-card deck, legacies, substitutions, and evidence through the standard MCP Apps bridge. Register the private tunnel-backed MCP connection in ChatGPT, then attach its verified app ID to the advisor through `.app.json`. A skill-only account plugin can load successfully while exposing no remote tools if that registered connection is absent. Verify native mobile access separately using current official developer documentation and direct client checks; responsive layout alone does not prove connection or rendering support.

The project also includes an optional read-only REST API for GPT Actions. It is a separate integration and may provide a text-only mobile route through a Custom GPT if the target mobile client cannot use the MCP app. GPTs can be used in ChatGPT mobile, but create/configure the GPT on the web and verify Actions in the target mobile client. This API does not render the embedded build view. Imports, inventory sync, and catalog publication remain in the MCP plugin.

## Primary plugin setup for web

1. Keep the MCP server and Secure MCP Tunnel client running on the persistent host. Follow the setup in [local-plugin-setup.md](local-plugin-setup.md).
2. Register or reuse the existing tunnel in **ChatGPT web → Plugins → + → Add custom MCP server → Connection: Tunnel**. Confirm that discovery returns the advisor's ten tools. Obtain the verified raw app ID from that registered connection's `.app.json` through Plugin Creator; do not substitute the browser's plugin ID.
3. Create the account plugin archive using the same tunnel and registered app:

   ~~~sh
   python3 scripts/package_chatgpt_web_plugin.py --tunnel-id "tunnel_..." --app-id "asdk_app_..."
   ~~~

   The archive contains instructions, `.app.json`, and a remote `mcp.json` tunnel binding. It does not contain local inventory, game data, tunnel credentials, or a server executable.
4. Use Plugin Creator to update the existing private advisor plugin while preserving its ID and audience. Verify the saved manifest references `.app.json` and its app ID matches the registered MCP connection. Create an advisor plugin only for a first installation.
5. Open a new ordinary ChatGPT web chat with Umamusume Build Advisor enabled. Verify manifest/profile reads, a server-specific recommendation, and the embedded Build View. A successful tool-discovery request alone does not prove these calls or rendering.
6. Test connection, tool calls, and Build View separately in the target native mobile app. Record observed errors or client limitations. The optional Custom GPT Actions route remains a separate integration, not an automatic fallback.
7. Check that the trainee, six support slots, legacies, ownership, substitutions, and citations remain readable on a narrow screen. The text response must include the same build facts, alternatives, assumptions, and evidence when the view is not rendered.

The source plugin folder also contains a `stdio` config for compatible local agents. Do not upload that local config as the ChatGPT account plugin; the packaging script replaces it with the remote Secure MCP Tunnel configuration.

## Optional alternate integration: deploy the read-only Actions API on the Pi

The API listens on loopback by default at port 8787. It requires a random bearer token of at least 32 bytes. Keep the API behind HTTPS and never commit its token or expose the private profile without authentication.

1. Follow docs/local-plugin-setup.md to install the public repository at ~/Sources/uma and configure the private repo path separately.
2. Build the Node bundle from ~/Sources/uma/mcp-server:

   ~~~sh
   corepack pnpm install --frozen-lockfile
   corepack pnpm build
   ~~~

3. Create a local service environment file with a random token. A 64-character hex value generated by openssl rand -hex 32 is suitable. Store the file at /etc/uma-build-advisor/actions.env with root ownership and mode 600. Include these settings, replacing the paths if the Linux account differs:

   ~~~ini
   UMABUILD_ACTIONS_TOKEN=replace-with-a-random-64-character-hex-token
   UMABUILD_ACTIONS_HOST=127.0.0.1
   UMABUILD_ACTIONS_PORT=8787
   UMABUILD_PUBLIC_REPO_ROOT=/home/<linux-user>/Sources/uma
   UMABUILD_PRIVATE_REPO_ROOT=/home/<linux-user>/Sources/uma-private
   ~~~

4. Install deploy/uma-build-advisor-actions.service.example as /etc/systemd/system/uma-build-advisor-actions.service, then run:

   ~~~sh
   sudo systemctl daemon-reload
   sudo systemctl enable --now uma-build-advisor-actions.service
   sudo systemctl status uma-build-advisor-actions.service
   curl http://127.0.0.1:8787/healthz
   ~~~

5. Install and sign in to Tailscale on the Pi. Enable HTTPS certificates and Funnel in the tailnet policy, then publish the local API:

   ~~~sh
   sudo tailscale funnel --bg 8787
   sudo tailscale funnel status
   ~~~

   Funnel gives the Pi a stable HTTPS hostname and forwards internet requests to the loopback API. Funnel is public internet access, so use only the read-only API and keep the random bearer token enabled. Its hostname is public metadata; catalog and inventory responses remain protected by the token. Tailscale configuration and approval must be completed in your own tailnet.

## Configure the optional Custom GPT Action

1. From ChatGPT on the web, create a Custom GPT if your current plan and workspace permissions allow it. Check the current [GPT creation and usage requirements](https://help.openai.com/en/articles/8554397-gpts).
2. Enable web search for the GPT. Build recommendations must check current Japanese-server strategy evidence at request time; static catalog facts and live strategy advice have different sources.
3. In the GPT's Actions configuration, import the complete OpenAPI file mcp-server/openapi/uma-build-advisor-actions.yaml. Replace its example server URL with the HTTPS hostname shown by tailscale funnel status.
4. Select API Key authentication with Bearer auth type. Enter the token from /etc/uma-build-advisor/actions.env in the GPT's secret field. Never paste the token into chat, source control, or a public issue.
5. Paste the full contents of docs/mobile-gpt-instructions.md into the GPT's Instructions field and save it. If the GPT Actions experience is available in your mobile client, open the GPT there and verify an authenticated catalog lookup and recommendation.
6. Start with a server-specific question, for example: “For Japanese server, suggest a medium-distance build for [trainee] for [scenario]. Use only cards I own or identify rental needs, and cite current JP strategy sources.”

## Action API contract

- GET /v1/catalog/manifest?server=ja|global returns the selected catalog's provenance and coverage.
- GET /v1/catalog/search?server=ja|global&kind=support_card&query=...&limit=10 finds records by name or exact ID.
- GET /v1/catalog/record?server=ja|global&kind=support_card&id=... returns the complete selected record.
- GET /v1/inventory/profile?server=ja|global returns only that server's private profile. Missing ownership is explicitly missing, not an empty collection.
- GET /healthz is an unauthenticated process health check and returns no repository or inventory details.

All data routes require Authorization: Bearer <token>, disable caching, and expose no write method. No browser CORS access is enabled.
